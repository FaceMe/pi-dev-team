How the factory runs workers

Workers are real pi --mode json subprocesses with a persistent session per role and ticket — so they reuse context and prompt cache, load your providers and extensions, and a crash never takes down your session. Every tool call they make passes the factory's guard: writes outside the ticket's scope are blocked, dangerous commands are refused, and gates are run by the factory itself — never claimed by an agent.

Headless too. Without a UI (print / JSON / RPC mode), /factory new accepts the prefilled answers and runs to completion — so the factory works from scripts and CI.
02 · software factory

/factory — from idea to merged branch

One command walks your project through nine phases, persisting to .factory/ between every step. You stay in control through a quick-setup screen, a bounded interview, and approval gates — the factory handles team assembly, test-first builds, reviews, gates and the merge.

§ Quick setup — one screen

/factory new [idea] opens a single screen of prefilled answers. Press Enter to accept them all, or open any line to change it. Your answers are remembered — team, autonomy and research for every project; the rest per folder.

§ The interview

  • At most 4 questions per round, each with a recommended answer and a "use your defaults" option; small ideas get one round.
  • Readiness checklist ends the interview as soon as every topic is known or assumed — unresolved topics become explicit assumptions in the spec.
  • Multi-model brainstorm for contested questions: the analyst fans out to several of your models — divergent, critical and pragmatic stances — then synthesises the options (≤ 2 per run).
  • Machine-checked spec — requirements with Given/When/Then, measurable non-functional requirements and traceability are validated before you see it.

PHASE 6 / 9

Build

Run by backendfrontendreviewer
  • Each ticket is built test-first by its role's worker inside the worktree.
  • Gates are run by the factory — install / build / typecheck / lint / test from the profile — never claimed by the agent. Out-of-scope changes are reverted before the gates.
  • A reviewer from a different model family approves each ticket's diff.
  • Failures retry with feedback, then escalate up the role's model ladder, then ask you.

stopsStops for you: budget breaker at 80%, a blocked ticket (every model tried), and — in careful — every ticket commit.
PHASE 7 / 9

Verify

Run byfactoryqa
  • Every gate runs on the integrated build with a fresh install; a red build becomes a critical bug ticket.
  • Exploratory QA: a read-only QA worker runs the software like a user — each requirement's acceptance criteria end to end, then invalid input, missing configuration and error paths — and reports bugs with reproduction steps and evidence.
  • Major and critical bugs become bug tickets (B-001…) that inherit the requirement's role and write scope and go back through the build loop — a QA-first regression test, the fix, gates, review, integration merge. The next QA round checks the fixes; at most two fix rounds by default.
Writes qa/round-<n>.mdbug ticketsqa/open-bugs.json
stopsStops for you only when bugs remain after the last fix round (balanced, careful): release with known issues, another round, or pause. auto releases and lists them.
PHASE 8 / 9

Docs

Run bydocscontributor
  • The tech-writer role produces the README, architecture notes, AGENTS.md for future agents, and a CHANGELOG.
  • Then the new-contributor check: a fresh agent clones the build and, using only the docs, sets it up, runs the tests and makes a small extension. The factory re-runs the documented commands and every gate in that clone; gaps go back to the writer for one fix round. The clone is thrown away.
Writes README.mddocs/AGENTS.mdCHANGELOG.md.factory/contributor.md
autoApproval: automatic in all presets — docs land in the worktree and go through the final gates with the rest.
PHASE 9 / 9

Release

Run byfactory
  • Final gates run one last time over the whole branch.
  • The branch is merged into yours when they pass — only if you're on the branch you started on and your tree is clean (in careful, you approve the merge itself).
  • An optional deploy always asks first — the deploy worker writes .env.example, never your .env.
  • The release is tagged v<version> locally (never pushed) and release notes list what was delivered, what verification fixed, and known issues.
  • The run finishes with .factory/report.md and a retrospective: cost by phase, escalations, failed attempts, and suggested follow-up tickets.
Writes merge to your branchv<version> tagrelease-notes.mdreport.mdretro.md
gateThe merge is yours: gates + clean tree + your branch, and your explicit approval in careful.

§ Guard rails

edit
Write scopes

edit/write outside the ticket's scope are blocked; an empty scope means read-only; .git/ is never writable. Anything that slips through is reverted before gates run.

deny
Blocked commands

git push/commit, history rewrites, sudo, publishing, piped remote scripts, rm -rf outside the project, fork bombs, and deploy CLIs — unless you approved a deploy.

gate
Gates run by the factory

Install/build/typecheck/lint/test come from the stack profile and are executed by the harness with real exit codes — "done" is never claimed by an agent.

peer
Cross-family review

Each ticket is approved by a reviewer from a different model family than the author's — catching the errors a family tends to share.

keys
No secrets stored

Deploy CLIs reuse their own logins; the deploy worker writes .env.example, never your .env; the reviewer is instructed to flag secrets in code.

merge
The merge is yours

Release merges only when the final gates pass, you're on the branch you started on, and your tree is clean — and in careful, only after you approve.

06 · fusion

The main / sidekick harness

Instead of one model for the whole session, a frontier main agent keeps the plan, the ambiguity and the final review — and delegates well-scoped mechanical work to a persistent, cheap sidekick with its own transcript, tools and prompt cache. Enable with /fusion on — Fusion always starts off, even on resume. Open the menu with /fusion or Ctrl+Shift+D.

main agent — frontier
this pi session · keeps the expensive prefix warm
  • owns the plan (numbered, each step (you) or (sidekick))
  • resolves ambiguity, makes the calls
  • writes delegation specs as data: acceptance criteria + verify commands
  • reviews the sidekick's changes before a run settles
⇄ sidekick(task, context, files,
acceptance, verify) ⇄ verdict first:
PASSED (checks 2/2 ·
acceptance 3/3)
sidekick — cheap
persistent in-process agent · own tools & context
  • targeted reads / greps, mechanical edits
  • runs tests, builds, installs — collects verbose output
  • answers every acceptance criterion in a checklist
  • tools: read, grep, find, ls, bash (+ edit/write optionally)
The harness verifies — not the model: after the sidekick finishes, it runs the verify commands itself (≤ 5) and puts a verdict first in the result, with exit codes, output tails, the acceptance tally, and the files changed (+12 −3 from git)  PASSED (checks 2/2 · acceptance 3/3)  FAILED (1 check failed)

§ Delegation modes — enforced, not just suggested

Telling a frontier model to "delegate by default" isn't enough when it holds bash and edit. delegation.mode makes delegation structural — switch anytime with /fusion mode strict|balanced|advisory:

Main agent may
  • read, edit, write, run commands
  • a test/build/lint/typecheck/install command runs directly the first time
  • once a command proved slow (≥ 60 s) or verbose (> 8k chars) it's redirected with a ready-made sidekick call
  • direct output > 8k chars gets condensed by the sidekick's model (full log kept on disk)
  • nudged after 6 direct calls in a row, or direct edits to 4 files in a run
Goes to the sidekick
  • everything slow or verbose once proven so
  • mechanical edits and repetitive reads
  • anything the main agent's plan marks (sidekick)
  • plan first: anything beyond a one-step change needs a numbered plan before action
Main agent may
  • read-only: read, grep, find, ls
  • bash limited to inspection — git diff/status/log/show, head, wc, grep
  • everything that executes or edits must go through the sidekick — Devin's "minimal direct action"
Goes to the sidekick
  • all execution and editing
  • with edit/write enabled in sidekick tools, it makes the changes; otherwise it reports what to change
  • relax rule: after 2 failed delegations the main agent's bash/edit come back — never stuck; strict returns with the next user prompt after a success
Main agent may
  • everything — full tools, no enforcement
  • the delegation discipline is advisory only (the old behaviour)
Goes to the sidekick
  • only what the model chooses to delegate
  • verification, caps and guard rails still apply to every delegation that happens

§ Guard rails in every mode

⏳
Commands that never exit are refused

Dev servers, --watch, tail -f, docker compose up without -d — refused with advice to use a one-shot variant or background with a log file.

⏱️
Default timeouts

Test, build and install commands without a timeout get one (commandTimeoutSec, 600 s).

✂️
Lean results

A sidekick result over 4k chars is capped; the full text is saved to a file the main agent can read.

📋
Better briefs

Every brief automatically lists the files the main agent has read (with line ranges) and git status — because the sidekick can't see the conversation.

🔒
No edit collisions

While a background delegation is changing a file, the main agent's edits to that file are blocked until it finishes.

🪜
Escalation & review gate

Two consecutive failed delegations escalate the sidekick one tier (small → daily → frontier). If the sidekick changed files the main agent hasn't reviewed, the run is held once for review.

§ Dynamic mid-session routing

A lightweight classifier scores the running task at each compaction boundary — where the prompt cache is invalidated anyway, so switching is free — and moves the main and/or sidekick model up or down the small → daily → frontier ladder. Routing is skipped in any session where you picked the model yourself (/model, Ctrl+P, --model).

  • llm mode — a cheap model scores the task, falls back to heuristic on failure
  • heuristic mode — keyword/regex signals only, no extra model call
  • auto-apply or suggest-only — suggested routes wait for /fusion route
